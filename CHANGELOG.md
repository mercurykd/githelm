## [Unreleased]

## [0.0.5] — 2026-11-22

### Added

- An open diff can be walked through the commits it belongs to. Two arrows join **Previous Change** and **Next Change** in the diff editor's own toolbar (`alt+[` / `alt+]`, and the same two commands in the editor's right-click menu; the palette stays hidden): `←` shows the diff of the commit before this one, `→` the commit after it, and the pair opened is always a commit against its first parent — the same pair the commit screen and the file log open. A single file walks that file's own history (`git log --follow`), so a commit that never touched it is skipped; a list of files walks the repository's first-parent history, one whole commit per step. The working tree is the newest end — stepping forward from the newest commit returns to the status diff the reader started from — a root commit is the oldest, and the ends, together with everything that is not a commit pair (a compare range `A..B`, a stash, a conflict stage, two files on disk), grey the arrows out instead of guessing. The rule a walk follows is settled by the diff it starts on and a step never changes it: a commit that changed three files is followed by one that changed a single file, and the walk goes on through the commits rather than turning into that file's history. Every step of such a walk is named after the commit it shows — `<sha8> — <n>`, one file included — because the commit is the unit being stepped through. VS Code cannot change the sides of an open diff, so a step opens the neighbouring pair in the same column and closes the one it replaced: one tab, cursor line carried over. Which diffs are walkable is a pure function over the two `git:` URIs (`src/git/diffWalk.ts`, tested against real repositories); the walking is `src/views/diffWalk.ts`, and a multi-diff tab is recognised by the per-file pairs its input reports — the property carrying them is `diffEditors` in newer builds and `textDiffs` in the extension host of 1.147, so both are read, and the title, which carries a `(3 files)` suffix VS Code adds on top of the one it was opened with, is only the fallback (matched through that suffix rather than by the plain title). The two icons are gated on the extension's own global context key rather than on `isInDiffEditor` / `inMultiDiffEditor`: those are set inside the scope of the pane that sets them, and whether a title toolbar sees one is that pane's private arrangement — depending on it left every multi-diff without icons.

- A commit's file list gained `t`: the files under the selection as the commit left them, one read-only tab each (`githelm.commit.filesAtRef`, in the panel and in the buffer, and the commit screen's hint line names it). `d` answers "what did this commit change", `t` answers "what did this file look like then", which otherwise needs the revision checked out — a commit is a state as well as a change. The files come from the object database through the built-in `git:` scheme (`openFilesAtRef()`, the opener a root commit's `d` already used), so nothing is written and the working tree is untouched.

- A folder that is not a repository has a panel too, so the UI that opens by default no longer has a case that hands the reader a text buffer: `git status` refuses such a folder, which is why the status model cannot be built for it, and the panel now draws the buffer's own `renderUninitialized()` document instead — the folder, the line saying it is not a repository yet, and `## init (1)` with its single row. The screen carries no `keys` column: that column lists the keys of a repository (`c commit`, `b branches`, `R reset`), and a folder without one has nothing for them to act on, so only the row's own key line is printed. `Enter` on that row runs the same `initRepo()` the buffer runs, and the init tab gives way to the status panel of the repository it created; `r` re-reads the folder, in case the repository was created in a terminal meanwhile, and moves on to the status panel. `alt+shift+g`, `githelm.webview.open` and a switch of the mode all land on that screen instead of falling back to a buffer, and switching back to the buffers closes the document, because it *is* the status screen of that folder. The render is the buffer's (`src/views/initRender.ts`, tested), the document is `githelm:init?<folder>` (`src/views/initScreen.ts`), and the key is one entry of the sub-screen keymap (`Enter: 'open'`), so `q`, `r` and the rows behave like those of every other sub-screen.

- Drag autoscroll: holding the button near the top or the bottom of a panel now scrolls it, so a range can be dragged past the rows that happen to be on screen. The farther into the edge band the pointer is, the faster it scrolls; the row that arrives under the pointer extends the selection, it stops at the end of the list and on `mouseup`, and the plain click, `Shift+Click` and `Ctrl+Click` paths are untouched. The arithmetic is a pure function (`autoscrollDelta()` in `src/webview/pointer.ts`, tested), so the speed is a number in a test rather than a feel.

- The lists tell a screen reader which row the caret is on. A panel never moves the DOM focus to a row — the keys are handled on the document — so `role="listbox"` said which list you were in and nothing about the row; every row now carries a slugged `id` (`row-line_3`, because a row id is a name like `line:3` or `src/a.ts`) and the listbox points at the caret row with `aria-activedescendant`, updated on every repaint and every selection change and cleared when nothing is selected. An arrow that walks the selection off the screen also brings the row it landed on into view, as the buffer scrolls after its caret.

- `git blame` is the file itself, not a picture of it. The document is the file's own text — the same lines, the same tabs, the same trailing spaces — opened in a real editor, so it is highlighted by the language VS Code uses for that file (the `languageId` is read from the real file and put on the blame's document), as wide as its longest line is, scrolled instead of wrapped, and selectable, foldable and searchable like any other file. The metadata is a decoration **in front of** the line rather than padding inside it (`BlameGutter`: one `before` attachment per line, 68 characters wide — 8 sha, 16 author, 10 date, 28 subject, a space between each and two before the code), so the code starts at one column and scrolls under the gutter; the box is also pinned to `68ch`, so the code cannot move even if a blank cell's padding is trimmed. A column is a **width**, which is what a line of text cannot have and a decoration can — and why the old padded table made the code a rendering of the file: no grammar starts a token at column 68, and a webview cannot run a grammar at all. A blame is therefore the one document that is not a panel in either UI: `openFileHistory()` sends a log to the panel in webview mode and a blame to the editor in both. The gutter is printed **once per block** — a run of lines from one commit is one cell and many lines of code, with the rest of the block blank and still 68 characters wide — and a line that is not committed yet prints `—` and `не в коммите` in the unstaged colour. The subject is cut to its cell with an `…`; the whole message — body and all — is the line's `hoverMessage`, `appendText`-ed so a message full of `*`, `_` and backticks is not read as markdown, which VS Code draws at the pointer over the text that was hovered. `git blame` does not print the message at all, so the blame is asked for the full sha (`--abbrev=40`, and `--root` so the caret of a root commit does not eat one of its forty columns) and the messages come from one `git show -s` per hundred shas rather than one process per row; a failed lookup leaves the blame exactly as it was. The parse still takes the date as its anchor, so an author with spaces or a line with parentheses stays whole. The cells, the popup and the client's grid went with the table.

- The sub-screens are panels too, and they are the last screens that were still buffers: a commit (`Enter` in the history, the tags or the log panel), a stash's file list, a conflicted file and a file's history all open in whichever UI `ctrl+alt+g` selects. A sub-screen is a **document**, not a stop of the carousel: its rows are the lines of that document (`line:3`), so click, `Ctrl+Click`, `Shift+Click` and drag select lines exactly as they select rows elsewhere, `Tab` has nothing to switch to in it and is not offered, and `q` closes it. The text is not re-rendered for the panel — each buffer gained a `prepare()` that writes the virtual document and its spans and returns its URI, `open()` is now `prepare()` plus the editor, and the panel calls `prepare()` and reads the same text and spans back — so the two UIs cannot draw two different patches for one file. Which UI a sub-screen opens in is the mode and only the mode: in buffer mode every tab is exactly what it was.

- `Enter` on a commit opens a **commit screen** instead of `git show`: the short sha and the subject, who wrote it and when, the full sha, the message when there is one, and then the files the commit touched — `M`/`A`/`D` and the path in the same list a stash prints. `d` on a row opens that file's change in the built-in editor (its parent against the commit; the file alone for a root commit), `r` re-reads the screen and `q` closes it. The list is `git diff --name-status -M` against the parent, so a rename shows its new path and a root commit is compared with the empty tree rather than failing, and the whole layout is one pure renderer (`renderCommitScreen()` in `src/git/commitView.ts`) shared by the panel and the buffer.

- A file list's `## files (n)` line is a header, not a title: a click on it selects every file under it, in a commit's screen and in a stash's as it already did on a status section, `Ctrl+Click` adds the list to the selection, and `Ctrl+A` is the keyboard's version of the same gesture. `d` then opens **one** multi-diff tab with every selected file — each compared with its own pair (the commit's parent against the commit, the stash's parent against the stash) — instead of only the first row, which is how a commit of twenty files was read one key and one tab at a time. A line that names no file (the author, the message, the key line) is skipped rather than failing the key, so a drag across the whole document diffs the files it crossed; `filesOf()` in `src/views/fileList.ts` is that rule in one place, and both UIs ask it. In the buffer the cursor and the selection play the same part — a cursor on the header and a drag over several rows diff the same files — so `d` means one thing in both.
- The conflict screen answers its keys from the panel: `o`/`Shift+T`/`Shift+B` take ours/theirs/base, `m` opens VS Code's merge editor (falling back to the file), `s` marks the file resolved, `r` re-reads the regions and `q` closes the tab. Each of those went from reading the active editor to taking the document's URI, which is what lets the panel act on the document it draws: the buffer commands are now one-line wrappers over the same functions, so the confirmations, notices and status-bar refreshes are the ones the buffer always had. Every file list — a stash's, a commit's — keeps its one key, `d`, and the key's answer is the built-in diff editor: the stash's parent against the stash, the commit's parent against the commit. A file's history is the exception: `githelm.log.fileHistory` on the history screen fills in the path of the screen itself (`showPath()`), because that screen already scopes its `git log` by path and a second copy of the graph as a sub-screen would be a second graph renderer.

- The submodules screen is a panel: `Shift+S` opens it in whichever UI the mode selects, and it lists what `git submodule status` reports — the initialised submodules, the ones that are not initialised, the modified ones and the ones in conflict, with the same `+`/`-`/`U` markers and the same reason line the buffer prints. `Enter` opens the submodule as a repository of its own (its status screen, `git init` included, or the buffer's note when it is not initialised), `u` runs `git submodule update --init`, `Shift+U` the same with `--remote`, `r` re-reads the list and `q` closes the tab. The keys run `runSubmodule`, the buffer's implementation, so the progress line, the notice and the status-bar refresh are the same in both UIs.

- The action log is a panel too, and it is the one screen of no repository: it lists every `git` call the extension made, newest first, with the clock and the command's exit code and duration — the same records, in the same order, with the same formatting the buffer prints. `c` clears it after the buffer's modal question (one helper, `runClearActionLog`, so the two UIs cannot ask different things about the same log), `r` re-reads the list and `q` closes the tab. The panel is opened with the empty path, so the status bar does not mistake the log for a screen of a checkout. Every screen now has a panel.

- The status screen as a webview panel (`alt+shift+g`), laid out like the text buffer it mirrors: `## section (n)` headers, a key line with a hairline under each block, the same monospace grid and the same theme colours, a `last commits` block, and the remotes/worktrees/stash column against the right edge of the panel with a readable width of its own. The layout follows the panel width, so hints wrap and the column moves under the list in a narrow window.

- In that panel: click, `Ctrl+Click`, `Shift+Click` and drag select rows, and a click on a section header takes the whole section; `s` stage, `u` unstage, `d` the built-in git diff — one multi-diff tab for the whole selection, the same view the built-in git extension opens —, `i` add to `.gitignore`, `D` discard with the buffer's layered confirmation, `c` the real commit buffer, `t` a tag on HEAD, `z` a stash of the selection or the working tree, `Enter` open the file, `Alt+S`/`Alt+U` everything, `g`/`b`/`T`/`S`/`l`/`h` the other screens, `Ctrl+A` select all, `Ctrl+C` copy paths. Keys are matched by physical key (`event.code`), so a Cyrillic layout behaves exactly like a Latin one. Row codes use the buffer's own palette (`githelm.*` theme colours), so `staged` is green, `untracked` warm red, `unstaged` amber, exactly as in the text buffer. Every piece of text takes the colour the buffer gives the same piece: section titles and paths by section, row codes by status letter, commit hashes, dates and authors, branch and remote names, so what is green here is green there. The text buffers are unchanged.
- One switch for the whole UI, on a key of its own: `ctrl+alt+g` flips the extension between the text buffers and the webview, and the keys inside a screen stay exactly the same in both. It is global, so it also fires from the panel itself, where the manifest keymap does not reach. The choice is remembered across restarts. Switching carries the screen you were looking at into the other UI instead of closing it — a status buffer becomes the panel and back, re-reading the same repository — and with nothing open behind it the switch opens the status screen, so the new mode is visible at once. Screens that have no panel yet keep their buffer in webview mode rather than opening nothing; the switch says so in the status bar. `alt+g` now opens the status screen in whichever UI the mode selects, and `alt+shift+g` still opens the panel but switches the mode with it, so the two implementations never end up mixed. The panel's own key line did not change.

- The panel's right-hand column is actionable, key for key as in the buffer: the arrows walk into it and a click selects a row, and on a row `f`/`P`/`U` go to *that* remote without the picker, `e` edits its URL, `x` removes it, `Enter` opens a stash's files or the other worktree's status screen, `Shift+Enter` and `Alt+Enter` open a worktree in a new window or reload this one, `a`/`p` apply or pop a stash, `d` shows its diff, and `A`/`n`/`W` add a remote, add a worktree or prune the list. The remaining keys that need no row work too (`m` amend, `f` fetch, `Shift+P` pull, `Shift+U` push, `Shift+R` reset, `Shift+M` abort an operation, `Shift+F` pull requests), all through the very functions the buffer commands call — same pickers, same modal questions, same notices. The host looks a row up again before acting, so a row deleted in another window reports "Cursor is not on an entry" instead of acting on stale data, and keys pressed anywhere else keep their buffer meaning (`Shift+Enter` on a file still opens the file).

- The panel keeps itself up to date instead of being a snapshot of the moment it opened: it re-reads the repository on the same quarter-second debounce the in-buffer status screen obeys — a `git` command run in a terminal (the index watcher), a saved document, and any command the extension itself runs — so staging from another window or committing from a shell shows up on its own, without `r`. Re-reading a hidden panel is skipped, and revealing it re-reads it anyway.

- The status bar behaves the same in both UIs. It names the repository of the screen that has the focus: with the panel focused and no text editor active, the panel's repository is the current one, exactly as an open status buffer names its own, instead of falling back to the first workspace folder (or hiding when that folder has no repository). Its branch and staged/other counters follow the panel's actions the way they follow the buffer's — staging, unstaging, stashing, discarding, tagging and the repository-wide keys all re-read it right away — and switching the whole UI with `ctrl+alt+g` refreshes it, since the screen it describes just changed host.

- The branches and tags screens are panels too, key for key as in their buffers. Branches lists the local branches (the current one marked `*`, the tracking label after the name, the subject underneath) and, after `Shift+R`, one block per remote; `Enter`/`c` checkout, `n` create from the branch under the cursor or from `HEAD`, `e` rename, `u` set the upstream, `x` delete with the buffer's own "not merged" follow-up question, `Shift+D` delete on the server, `m` merge, `d` compare, `Shift+S` reset with the mode picker and the hard-reset question, `r` refresh, `q` close. `d` asks the history screen's six questions about branches — one row against `HEAD`, two rows against each other — and answers them without a text buffer: `log …` hands the range to the history screen (so the graph of `A..B` is drawn by the screen that draws graphs, with `x` to go back), `diff …` opens the built-in multi-diff at the two tips. The buffer's `d` runs the same plan and opens its patch window or its history window. Tags lists every tag with its annotation, sha, date and author: `Enter` opens the tagged commit on the commit screen, `t` creates (annotated, if you give it a message), `e` moves the tag to `HEAD` after a confirmation, `x` deletes, `Shift+U` pushes against the value the remote has and offers to overwrite when they differ, `Shift+D` deletes it on the server, `r` refresh.

- Those two screens are one panel per screen, like one buffer per screen, so branches and tags are tabs next to the status panel and the keys of each stay the buffer's. Every key goes back through the host to the *same* function the buffer command calls — the row's name is looked up in the repository again — so a picker, a modal question or a notice is word for word what the buffer shows, and a key pressed on a stale row reports "Cursor is not on a branch" instead of acting on the wrong thing. The panels re-read on the same deps refresh as the status panel, and `Shift+R` on branches is the one key that stays in the panel, because it changes what the screen shows rather than the repository.

- The panel reports progress where the buffer reports it, through the same table and the same status-bar item: `f` shows the spinner and `fetching…` while it runs and ends with `Fetched.` for four seconds, `P`/`U` say `pulling…`/`pushing…` then `Pulled.`/`Pushed.`, and `Shift+R`, `Shift+M`, `m`, `z`, `c` and a fetch of a remote row likewise. Keys that are instant in the buffer stay silent here too. Going through that one path also means a failure from a panel key reaches the log and the error popup instead of vanishing, and that `z` asks the buffer's own questions — stash options when no file is selected, then a stash message — instead of stashing silently.

- `Tab` and `Shift+Tab` walk the screens as a carousel — status, branches, tags, log and back — **in the tab you are in**: the screen you leave closes and the next one takes its place, so pressing `Tab` never adds a tab. The walk wraps both ways, and the next screen is opened for the repository of the screen you came from, so the carousel stays on the same repository. The key belongs to the panels only: the text buffers keep `Tab` as the editor's key, and the key line the two UIs share is untouched — the panels print their own `tab switch screens` hint beside it.

- The history screen is a panel too, and the graph is not redrawn there: the rows are the ones `logRows()` produces for the text buffer, split at the buffer's own spans, so the graph is the same character grid, the columns line up the same way and every piece takes the colour the buffer gives it (the graph in its own grey, the sha, the date, the author, the refs in brackets). Same keys as the buffer: `Enter` opens the commit, `n` branches from it, `c` checks out its ref, `C` cherry-picks, `V` reverts (with the mainline question for a merge), `f` fixups onto it, `R` resets to it with the mode picker, `t` tags it, `d` compares one row with `HEAD` or two selected rows with each other, `a` shows all refs, `/` puts the caret in the filter input, `x` clears them, `s` cycles the order, `r` re-reads, `q` closes. Every key runs the buffer's own code (`runLog`), so the questions, the notices and the progress lines are word for word the same. `d` is the exception, because the buffer answers it by opening a compare window: the panel answers the same six questions in place instead — a `log …` choice becomes the panel's own range (`A..B` in the header, `< >` and the `<`/`>` row markers for `A...B`, `x` to go back) and a `diff …` choice opens the built-in multi-diff editor at the two revisions, so comparing never drops you into a text buffer. The screen is read a page at a time — 200 commits — and scrolling to the end asks for the next page, which is added under what you have already read without moving your place. The filters are inputs above the history rather than a table beside it: the grid needs the full width, so the fields sit in one row, each box named by the buffer's label as its placeholder, and `Enter` in one asks git for exactly that field. A filter is a `git log` argument, not a sieve over the visible rows: it searches the whole history the screen walks (`HEAD`, every branch and tag with `a`, the two refs of a range while one is shown), and the page limit applies to the matches — the first page holds the newest *matches*, however deep they are, and scrolling adds older ones.

### Changed

- The webview is the UI: every screen is a panel, and the switch that used to sit beside it (`ctrl+alt+g`, the stored mode) went with the buffers — see **Removed**. The default is read from a missing `githelm.uiMode` rather than written into it, so it is a default and not a conversion — a profile that never chose stays with the panels across upgrades, and a reader who did choose the buffers keeps them (`mode.ts` reads only an explicit `buffer` as buffers, everything else as panels). One switch still moves the whole extension, because `parseUiMode()` is asked once at activation and `screenHost()` answers for every key after that.

- Every diff in the webview is VS Code's own diff editor: `d` on the status panel opens the selection as one multi-diff tab (staged rows read against the index, unstaged ones against the working tree — the pairs the built-in git extension compares), `d` on a file of a commit or a stash compares its parent against it, and a range compare opens the two tips. The generated patch panel and its `alt+d` are gone: a patch that only looks like a diff is worse than the editor at every job the reader has, and two keys for one verb is one key too many. Half a file is the one thing the editor cannot stage, and a hunk has line numbers only in the text buffer's patch, so hunk staging stays there; whole files stage from either UI. A file the git extension cannot serve (a conflicted path with no base stage, say) reports it instead of silently opening a patch in its place.

- The help screen is gone, from both UIs: every screen already prints its keys under the title, so `h` opened a second copy of the line that was on screen. `h` and `githelm.help` went with it — the `githelm.help` *colour* stays, because it paints those hint lines. The key lines themselves are untouched, save for the `h help` entry that used to end each one.

- The tag rows of the panel are a table, not a list: the name, the annotation, the sha, the date and the author are padded to the widest value of the screen with the same arithmetic `renderTags()` uses, so the sha, the date and the author sit under each other exactly as they do in the text buffer, and a tag without an annotation keeps the column instead of pulling the row left. Copying a row still copies the tag name alone.

### Removed

- The text-buffer UI is gone: every screen is a webview panel now, and there is no second interface to keep in step. Removed with it: the UI switch (`ctrl+alt+g`, `githelm.ui.toggle`, the stored mode), the `githelm.webview.open` command, the `githelm.ui.hintColumn` setting and the `githelm.view` context key. The manifest went from 95 commands and 92 keybindings to 21 and 3 — `alt+g`, `alt+[` and `alt+]`; the other 89 keys live inside their screen now, where the panel reads them by physical key code, so a Cyrillic layout still works. The modules that drew a screen as text for an editor went with them (`statusRender.ts`, `logRender.ts`, `branchesRender.ts`, `tagsRender.ts`, `submodulesRender.ts`, `actionLogRender.ts`, `columns.ts`, `mode.ts`, and the twelve `*Buffer.ts` documents), and each screen's body lives in one place: `commitDoc.ts`, `stashDoc.ts`, `conflictDoc.ts`, `historyDoc.ts` and `initRender.ts`. Nothing became unreachable — a panel runs the same git operation the buffer's command called, and asks the same questions first. Blame stays a real editor, because a webview has no grammar to highlight code with: it is the one `githelm:` document left.

### Fixed

- A commit's tags and branches are on its row in `## last commits`. The refs were there all along — `readLog()` asks git for `%D` and the history screen prints it — but the block's model kept only the sha, the date, the author and the subject, so the head commit of a release looked like any other commit and a tag could only be found in the history. The row now carries the refs in the history screen's own notation (`[HEAD -> main tag: v0.0.4]`) in front of the subject, in the `refs` colour, in the same grid cell as the subject so a commit with no refs leaves no empty column. `refsLabel()` in `src/git/log.ts` — the function the history screen already used — formats it, so the two screens cannot disagree about how a ref is written.

- A commit subject longer than the panel wraps under the subject column, not under the graph. The history row is one string, so its `pre-wrap` continuation started at the left edge and a wrapped subject read as a row of its own, with no graph and no sha beside it to belong to. The row now reports the column its subject starts at (`LogRow.subjectStart`, which a refs label in front of the subject moves row by row), and `.log-line` uses it as a hanging indent — `padding-left` puts the continuation under the subject, `text-indent` pulls the first line back to the edge. Wrapping also breaks between words before it splits one — `overflow-wrap: break-word` rather than `anywhere` — so a subject wraps where it reads.

- Every diff the extension opens in the built-in editor is now titled the way the built-in git extension titles its own. Both sides of a `git:` diff carry the same path, so an untitled `vscode.diff` left two indistinguishable tabs and said nothing about *what* was compared: a staged row is `src/a.ts (Index)`, an unstaged or conflicted one `src/a.ts (Working Tree)`, an adopted untracked file `src/a.ts (Untracked)`, and a pair of revisions `src/a.ts (stash@{0}^) ↔ src/a.ts (stash@{0})` or `src/a.ts (a1b2c3d) ↔ src/a.ts (dc3ba5e)` — the side names in the reader's language, a full sha cut to eight characters. The multi-diff tab keeps its own title (`stash@{0} — 3`), so a tab of twenty files still says which two revisions it opened. `sectionName()` and `refName()` in `src/webview/panel.ts` hold the rule; the smoke test asserts the exact titles of five tabs.

- In a panel, `d` on a stash row failed with git's own error instead of opening the diff. The row was planned as the range `^..`, and `^` alone is not a revision: `git diff --name-only ^..` exits 128, so the key ended in `fatal: bad revision '^..'` with no diff at all. A stash row now means the whole stash — its files are read with `stashFiles()`, the reader its own screen uses, and every one of them opens in one multi-diff tab, its first parent against the stash itself: exactly `git stash show -p`, in the editor. The status screen's `d` and the panel's row target share one `openStashDiffInEditor()`, and an empty stash says so instead of throwing.

- The `Enter` of the numeric keypad works like the one above the letters, in both UIs: keys are matched by physical code, and `NumpadEnter` was not in the map, so it reached VS Code instead of the screen. `NumpadDivide` follows `/` for the same reason.

- After `q` closed a panel, the keys of the screens stopped working until the user clicked back into one: closing the last tab of an editor group leaves the focus nowhere. The focus now goes to the next screen that is still open — and to the editor group when none is, where the buffers' keys belong.

## [0.0.4] — 2026-11-19

### Added

- `alt+s` stages every change in the repository, deletions included, and `alt+u` takes all of it back out of the index. They sit next to `s` and `u`, which keep working per file, per section and per selection.

### Changed

- The `keys` column of the status screen sits a little left of the shared column: with two more keys the hints ran past the right edge of a normal window.

### Fixed

- The tag commands no longer appear in the Command Palette, where the extension keeps nothing but its three entry points.

## [0.0.3] — 2026-11-19

### Added

- Refreshing the status screen says so in the status bar: `r` used to be silent whenever nothing in the repository had changed, which reads as a dead key.

### Fixed

- Windows: after initialising a repository from the status buffer, the buffer kept showing the text of the first render — `r`, `s` and `u` reached git but the screen did not follow. The document was keyed by the folder in one spelling (`D:\…`, what VS Code hands over) and re-rendered in another (`D:/…`, what git prints); both are one path now, and a buffer remembers the folder it was opened for.
- The branches screen stayed empty in a repository without commits, although the status screen reported the branch: a branch that `HEAD` points at but that has no commit is not a ref yet, so there was nothing to list. It is shown now, with a `no commits yet` note.
- Stage, unstage, diff, discard and ignore answered "Not on a file or a section header" when the cursor was on an empty section header. An empty section now says so instead.
